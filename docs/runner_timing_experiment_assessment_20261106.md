# runner 里程碑计时实验评估（2026-11-06）

## 是否值得执行

该实验有有限判别力：它可以用总耗时旁证前台启动脚本是否至少运行到了某个阶段，并检查公开话题是否有发布者或一次消息；它不能证明源码已经由平台编译成功，也不能证明消息被正式裁判接受，更不能替代真实巡检任务。

现有记录提供了粗略基线：前台 `sleep 10` 记录约 21.1 秒，前台探针 `sleep 30` 记录约 41.2 秒，表面上都接近“脚本时长 + 11 秒”。但这不是严格对照，因为脚本内容不同，且平台可能把裁判启动、队列和收尾时间纳入耗时。此前 `gnome-terminal` 记录与脚本睡眠时长不一致，所以计时实验不能使用 GUI 包装。

## 最小设计

先使用与实验完全相同的前台脚本结构做一次 clean baseline：source ROS 后立即退出，或只保留最终 `sleep 0`。然后至多提交一次自适应诊断脚本，让它在每个阶段选择不同的最终 sleep：

| 阶段 | 建议最终 sleep | 含义 |
| --- | ---: | --- |
| ROS setup/source 失败 | 4 s | 只说明 shell 已进入脚本并能执行分支 |
| `import rclpy` 失败 | 14 s | ROS Python 运行时不可用 |
| 公开图检查无发布者 | 24 s | 目标公开话题在用户域没有 publisher |
| `/odom` 成功收到一次消息 | 34 s | 至少有一次地面里程计回调/消息到达 |
| `/referee/ground_tasks` 成功收到一次消息 | 44 s | 至少有一次任务话题消息到达 |

各分支之间相隔 10 秒，全部分支最后以退出码 0 收尾，避免平台因非零码提前终止。预计总耗时约为最终 sleep 加平台固定开销；按已有约 11 秒估计，最高约 55 秒，应保留平台硬超时和队列抖动余量。脚本必须前台运行，不使用 `gnome-terminal`、`exec bash` 或后台子进程。

这五档最多编码“第一个失败里程碑”。如果还要单独编码“所有阶段都通过”，需要第六档，最高 sleep 会再增加约 10 秒，连同既有固定开销可能接近或超过平台硬超时；在没有明确超时合同前不应增加这一档。

## 判定与局限

- 以“自适应记录总耗时 − clean baseline 总耗时”判断落在哪个 10 秒区间；只有差值明显大于已测的 1–3 秒级抖动时才接受阶段判断。
- 若总耗时接近固定超时、区间跨越边界、或与历史睡眠基线不一致，只能判定计时不可用，不能选择某个阶段。
- 公开话题的 `Publisher count=0` 只能说明当前用户域无发布者。用 `ros2 topic echo --once` 判断消息可能受类型/QoS影响；`/odom` 和 `/referee/ground_tasks` 的真实类型、可靠性和持久性尚未得到官方合同，假阴性风险较高。动态 `rclpy` 回调更接近目标，但仍需要运行时能解析实际消息类型。
- 实现时必须在 `source` 周围暂时关闭 `set -e`，并给 `ros2 topic info`/`echo` 设置短 `timeout`；否则 source 或 ROS CLI 自身的非零退出、守护进程等待会绕过 sleep 分档，令计时不可解释。
- 该实验仍不会让只读探针产生裁判结束标志。若测评配额有限，或平台不提供用户日志且没有明确硬超时，实验的证据强度为中低，不建议为了它继续消耗配额。

## 结论

计时实验最多回答“前台脚本是否执行到某个公开通信检查”，不能回答“为什么正式测评没有成绩”。正式阻塞仍需平台提供同一 run 的编译命令、工作目录、用户 stdout/stderr 和退出码，或提供官方已知可运行的巡检工作空间作为对照。
