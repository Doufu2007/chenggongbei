# 当前巡检接口确认与剩余缺口

更新日期：2026-11-12（北京时间）。本报告结合官方《应急救援机器人挑战赛裁判系统判分细则 V1.0》、测评注意事项、当前工程配置及本队平台只读探针证据。v5 已取得完整诊断快照、14 类真实公开消息样本和两张相机诊断 JPEG，证明探针节点运行；完整任务仍未计分或通过。v5 的 5 条网络事件中缺少 `probe_started`，不能声称收到该启动事件。证据及 `failed + score:null` 终态见 [platform_probe_v5_20261112.md](platform_probe_v5_20261112.md)。

## 来源与适用范围

- 官方课程：[应急救援机器人挑战赛裁判系统判分细则 V1.0](https://www.splenach.com/api/courses/129d6e75-f19a-4c97-9ec6-0853695a4c48)。本地保存为 `docs/referee_rules_v1.html`、`docs/referee_rules_v1.txt`、`docs/referee_rules_v1_api.json`，重点是表 1、巡检任务流程、表 3 与表 5。
- 用户提供的《ROS 仿真测评系测评注意事项》：`/odom`、`/uav/odom`、`/tf` 作为公开位姿来源；白名单保留 `/referee/ground_tasks`、`/referee/current_target`、`/referee/recognition_status` 等；禁止真值、随机化答案文件、原始裁判事件与自启仿真/裁判。此须知确认可用接口名称，但没有给出所有消息 schema。
- 当前配置：`src/inspection_mission/config/interface_profile.json`、`mission_plan.json`、`inspection.yaml`。当前 `verified:false`，地图和外参未填的值仍保留为空。

官方 V1.0 自述为暂行版本，后续若有修订须按最新官方内容更新。论坛用户帖只作为查找资料的线索；不再把已经有官方来源的 CSV、话术、声明值标为“只凭论坛猜测”。

## 表 5 话术边界

地面与空中图片类别为：坍塌废墟、滑坡塌方、被困人员、受损车辆、救援营地。窗口类别为：救援无人机、飞鸟。

- 地面话术：`发现{类别}，地面巡航任务点确认，将巡航信息发送回指挥中心。`
- 空中话术：`发现空中巡航任务点，识别目标为{类别}，执行灯光提示，将巡航信息发送回指挥中心。`
- 窗口话术：`发现窗户上方目标为{类别}，执行下降避让，穿越窗户。`

这些话术来自官方表 5，可以作为固定输出模板；本局目标类别必须来自相机的真实、足够清晰且与当前物理点关联的观察。不能轮流发送五种类别试探裁判，也不能预填随机化结果。QR、ArUco 与 ORB 算法可用，不代表官方图片必为二维码或 ArUco；未取得目标图库时不存在已验证的类别识别能力。

## 识别确认仍未确认

测评须知列出了 `/referee/recognition_status`；2026-11-11 平台公开图与类型发现已确认其为 `std_msgs/msg/String`，字段 `data:string`，发布端 QoS 为 RELIABLE/VOLATILE。**尚未收到其实际 data，状态值、回执格式、关联语义和更新时间仍未知。** 官方规则要求“判定正确后”进入下一动作，并不等于“裁判回传参赛方自定义 UUID”。

当前默认配置的识别确认字段仍未绑定，属于实质阻塞项。通用 event_ack 解析要求明确布尔接受值和 ID；控制器用本局 `session_id:serial` 关联报告。但表 5 的官方识别载荷是中文话术，没有证据允许附带该 UUID 或证明裁判回传它。显式 transport_only 已不订阅或等待未绑定的 ACK，不填充接受集合；这只是本队传输合同，不解决裁判认可证据缺口。

需要官方提供真实的 `ros2 interface show`、一条允许的脱敏状态消息与更新时机，明确：它按点 ID、类别、报告 ID 还是已识别集合关联；是否包含局次/时间信息；否定和重试如何表达；地面、窗口、空中是否共用确认方式。获得后才能实现对应关联，防止把历史接受状态误用于当前点。

## 验证与下一步

已实施的 CSV、5 选 3、话术映射、内部/官方话题隔离、地面点前识别与进入声明、空中报告先于照射，以及窗口和降落前声明，均以实际测试记录为准。纯 Python 测试验证代码行为；独立的平台 v5 探针另已证明节点运行、公开抽签与14类消息接收。完整业务控制、目标识别、物理运动或官方得分仍未证实。

接下来根据实收相机/CameraInfo、TF 和传感器核验候选资料，补齐仍为空的地图、光学外参、控制接收端和确认解析，再测地面识别→进入→声明、窗口声明→识别→下降→穿越、空中识别→确认→有效照射、返航→降落前声明→实际落地→官方结算。当前 `verified:false` 应保持，直到上述合同有证据且能通过启动校验。

最终成功依据是官方场景中的真实完整任务与有效成绩；只读探针退出、本地 COMPLETE、网页默认 0 分或人工构造结束文本都不是该依据。

## 2026-11-11 飞行与照射的实质缺口

前向点云的停止体积与传感器视场不匹配，当前分支不能覆盖必需的起降、下降、爬升、偏航和后退。前视相机持续居中与下视激光位于地面目标正上方的照射几何也存在冲突。必须依据真实机体包络、传感器外参与自由空间证据修正飞行合同，并把目标定位和后续照射分阶段验证；不能删门禁、缩小机体或刷新旧检测时间戳。审计与修复方向见 [flight_contract_audit_20261111.md](flight_contract_audit_20261111.md)。
