# v35 恢复账本与 v38 资源合同候选（只读方案）

结论：全程 3 次恢复是有限实验的恢复频次/资源预算，并非数据新鲜度或净空的物理准入阈值。它仍是防止无限重试的辅助边界，修改须使用独立版本并预先冻结。v35 首点识别前已恢复 3 次，而累计 PAUSE 仅约 3.291s；v33 也发生 3 次恢复。保持该次数上限直接叠加相机恢复机制，容易在第一次相机缺帧时已经没有名额，不能据此评价相机恢复机制是否正确。

本方案按主代理接受的候选值拟冻结为：**全程最多 32 次成功恢复、单次 PAUSE 最长 5s、累计 PAUSE 最长 60s、全局创建起最长 1200s**。保持每点相机新 epoch 重采最多 1 次；该重采恢复也计入同一个全程 32 次预算，不在点切换时清零。此处仅提案，尚未实现或上传；v36 先独审机制，v38 再独审资源适配。

## 32/5/60/1200 是否合适

32 次是 v35 已观测恢复次数的约 10.7 倍，避免“首点已用满 3 次”这一已知直接障碍。单次 5s 是本局最长约 1.165s PAUSE 的约 4.3 倍；累计 60s 最多占总合同 1200s 的 5%。若 32 次都与本局最长暂停相同，累计约 37.28s，仍落在 60s 内。这是可测量的工程试验余量，不是概率成功保证；不能将 3 次短样本外推为“32 次足够覆盖全路线”。

因此，**32 次是合理的下一次有界试验候选，现有证据不足以判定它保证足够，也没有依据认定它过宽**。额外频次只允许更多“已恢复合格后的动作”，单次和累计等待上限同时限制长期抖动；若候选仍因资源预算停止，应记录真实耗尽原因，不在同局临时加码。32/5/60/1200 必须在运行前冻结，不能在中途根据暂停次数调整。

## 不改变非零命令准入

源码 `ground_three_point.py:375-387` 在 PAUSE 恢复前先检查故障与 `_stable_dwell()`，随后才检查/递增 `resume_count`；计数并不代替新鲜度或停稳。`ground_bounded_approach.py:150-162` 的全局/阶段墙钟持续计时，`:193-223` 的姿态、速度、永久路径/旋转及本地扫描运动余量持续有效，`:226-232` 仍要求原 `_condition()` 与 scan anchor。`:338-351` 静稳门保持源/墙双至少 1s、线速度≤0.01m/s、角速度≤0.03rad/s、anchor 位移≤5mm、四元数角差≤0.02rad。

axis adapter 在最终 DDS 查询之后重新 step，并在任何非零发布之前再次执行 `_budget_fault/observed_motion_fault/_condition`（`ground_three_point_axis.py:325-338`）。新资源合同必须经过这些原检查，不能缓存恢复前的非零 decision。PAUSE 始终只能零输出；过龄 odom/scan/clock、过大的负采样差、净空不足、anchor 不可用或任一运动硬故障均不得因剩余次数而准入非零。

保持 `sensor_age_s=0.20`、当前相机活性 `0.50`、prior 最大差 `0.05`、合法负采样边界 `−0.12`、净空/速度/路径/旋转及阶段截止不变；各阶段/全局起算点与永久账本均不因暂停、重采或点切换而重置。对于已观察到的 clock 样本抖动，原机制已成功停车恢复 3/3，增加有限资源名额足以避免这三次“仅因次数预算”阻断；尚不能保证未来任意抖动都能在 5s 内恢复。

新增测量应保留每段 `pause_enter_wall/exit_wall/reason`、进入及恢复时 timing、episode index、成功 resume index、当前段与累计 pause wall、计数与三个时间上限的 freeze 值；当前进行中的 pause 也计入累计。反复收到同一 freshness 故障不能重新开始 5s 计时；只有真正退出 PAUSE 才封账，随后新 PAUSE 才开新段。count 只在全部恢复门通过后递增一次；次数已满时停止，不能多恢复一次。

## v38 外层适配注意点

冻结父类中的 `resume_count >= 3` 不必修改。新的最外层 step 对每个允许恢复的 `state==PAUSE` 分支拥有完整恢复逻辑，先检查原故障/新鲜度与资源预算，再完成原双时钟停稳。合格时将**真实** `resume_count += 1`、恢复原 phase，并在该次调用返回零，父层此后只接收非 PAUSE 状态；下一 tick 的非零命令仍完整经过 axis adapter 最终检查。禁止清零、临时减小、影子化或伪造 resume_count 以穿过父类上限。

外层接管必须保留 v36 已冻结的恢复许可与视觉生命周期：只有 v36 允许的相机临时缺帧且识别未 attempted 才能新 epoch 重采；每点重采一次仍真实计数；REPORT_WAIT/attempt 后、非法 header、倒退及规定的不可恢复故障继续锁停。不能因为接管所有 PAUSE 而绕掉 v36 的 epoch/recapture 更新，也不能让资源层重新分类任何硬故障。实际恢复 phase、new epoch 和计数只更新一次，不通过临时改 state 调用父层来“借用”恢复。

单段 5s 与累计 60s 要在 `_budget_fault`、watchdog 及活动回调检查中生效，包括当前未结束 PAUSE。反复故障不能重设入段时间；STOP/FINISHED 不可被恢复。永久总账、全局/阶段 deadline 的起点保持原值。证据明确报告外层 owner/revision、真实 max_resumes=32、真实计数和 pause 序列；继承证据里的 hardcode `max_resumes=3` 应由外层覆盖为实际合同，并保留父层合同来源说明，避免回传继续声称仅允许 3 次。记录容量至少覆盖 32 次成功恢复加最终未完成段，建议 40 段，丢弃必须有计数。

## 少量可判别反例（合成验收场景，不是平台数据）

1. 重复 32 段 1.165s PAUSE，每段恢复均 fresh+静稳：允许至第 32 次，累计约 37.28s；第 33 次即使 fresh 也必须以次数预算停止，不能发新的非零。真实 resume_count 必须为 32，不能变为 0、2 或其他代理值。
2. 单段在 4.2s 才 fresh，之后还需双时钟 1s 静稳：必须在该段 5s 处资源停止，不能延至 5.2s 恢复。每 20ms 重报 freshness 故障也不能重置这个计时。
3. 连续 12 段 4.9s PAUSE 已累计 58.8s；第 13 段进行到 1.2s 即达 60s，应立即停止，即使次数远未满。累计判断不能仅在退出 PAUSE 时做。
4. 次数/时间都剩余，但 `clock−odom=−0.14`、odom/scan 墙龄 0.21s 或净空不足：输出仍必须为零。之后 fresh 恢复时须从合格 anchor 重新完成双时钟停稳，禁止使用暂停前缓存的非零命令。
