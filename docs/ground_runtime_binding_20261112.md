# v5 真实公开样本与首个地面点计分合同复核

日期：2026-11-12。范围仅为本地证据、官方已缓存规则、公开候选静态文件的只读核查。本轮没有联网、发布 ROS 消息、运行仿真、修改业务程序或配置。唯一新增文件为本报告。

## 结论

v5 已证明用户源码可以启动并接收真实公开传感器、相机和本场抽签消息；不再是“只有裁判启动日志”的阶段。但本次用户域图中**未发现任何命令/上报通道的订阅者**，也没有命令响应、正确识别、到点接受或平台得分证据。首个地面点仍不能诚实标为可执行或已计分。

最小下一局应从纯只读探针切换为**有实际输出、受限的地面控制验收**：建立文档规定的命令发布端，确认用户域订阅端和 QoS，在本局新鲜传感器通过停止条件后做一次至多约 2 cm 的低速直行并停止，用公开里程计和前后真实图像验证响应。只在本场首点的 ID—区域映射和真实视觉类别均已建立后，才继续该首点的识别—进入—到点声明；不得用猜编号、猜坐标或轮流上报类别来试分。下面给出了这两层的具体完成标准。

## 真实抽签、位姿、TF 与传感器

### 本场任务顺序

`/referee/ground_tasks` 首样本为 `String.data="ground_1,ground_4,ground_0"`，计数为 1。接收端须保留此顺序；每次运行重新读取，不能固定本次抽签。该证据新增确认 **`ground_0` 的确在本场合法 ID 中**，但没有证明全套五个 ID，也没有证明 `ground_1` 对应哪个 world 模型。

`/referee/recognition_status` 现在已发现实际类型为 `std_msgs/msg/String`、字段只有 `data`；没有该话题消息样本，因此仍不知道字符串载荷、接受值、关联点位或事件语义。`/referee/events_public` 同样只有图和 schema，未收到内容；不能把它当识别回执。

800×800 的 K 对应约80°水平视场，与候选静态 world 相容；这不是平台版本等同证明。UAV 的 P[3] 对应候选 world 的 `hack_baseline=0.07`，**不是光学相机到机体的平移**，不能拿它替代外参。

`camera_link` 这样的名字不证明坐标轴采用机体前左上或光学右下前。渲染相机 link 的姿态、ROS header frame 和 OpenCV tvec 的光学轴之间的完整变换必须明确。现有 TF 首样本没有这条链；地面相机首图全绿也不能单独证明镜头朝下、被遮挡或故障。应通过受限移动后的多帧真实图像、明确 frame 变换和场景观察核对，而非把候选 `rpy=0` 当作实际轴合同。

候选 world 的地面相机是机体平移 `(0.16,0,0.11)`、姿态 `(0,0,0)` 的前向相机；机体静止 z≈0.055 时，相机约 z=0.165 m。若目标确在静态任务平面 z≈0.012 m，且80°垂直视场、无遮挡、外参都成立：

- 目标中心在相机前约 **0.182 m** 以外才进入图像下边界；进入视场不等于能识别完整图片。
- 以当前控制器 `center_tolerance=0.12` 的归一化中心门限计算，地面中心需距镜头约 **0.760 m** 以上才可能满足垂直居中门限。越接近、越到正上方，水平前视相机越难维持居中。

这只是候选几何条件推导，不能据此给实际相机添加默认外参或断言其一定能看任务图。它提示地面也应“点外可见位置识别→地面进入点位→到点声明”，不要强求在点位正上方仍有前视居中图像。官方规则本来就要求入点前识别。

## 首个地面点得分仍缺的最小条件

官方 V1.0 的10分/点条件是“识别话术匹配正确且进入点位”。执行顺序为：读取公开三点抽签→按顺序地面导航→在进入前识别本点实际图片并上报对应话术→进入点位→发布本点 `current_target` 到点声明。地面过程不得发非零 `/uav/cmd_vel`。

目前缺口：

1. 用户向官方方向的 `/cmd_vel`、`/inspection/detections`、`/referee/current_target` 通信链实际响应，含订阅端/类型/QoS或其他可靠的物理/接受证据。
2. 当前首个随机 ID 的区域/坐标映射，以及 odom 与该地图的对应；候选 world 坐标不能直接当已验证。
3. 点外可见的真实目标图像及可靠类别。当前地面首图没有可识别内容；已有图库/识别器尚不能替代当前帧证据。
4. 地面雷达/相机的实际 frame、外参与机体包络；至少能支撑这段地面导航和停止，不必等空中完整几何。
5. 识别接受/点位状态的可用进度合同，或终局结构化诊断。虽已知 recognition_status 是String，仍不知其载荷语义。不能编造 `accepted` JSON字段；若用明确配置的 transport-only 推进，必须把它标为本队发送行为，不能宣称裁判确认。
6. 练习结束后能提取官方逐任务成绩。shell退出0或本队阶段完成不满足这个条件。

当前默认 `interface_profile.json` 仍 `verified=false`，ground/uav frame和命令topic未绑定；`mission_plan.json` 坐标、外廓为空，ID为未核实占位符 `ground_1..5`。不得为消除门禁而改 `verified=true`、填猜测的 ID/坐标或缩小机体。

## 建议下一次：地面输出建链与微位移验收

这是一局实际地面动作练习，不再提交只读探针，也不冒充完整比赛任务。

1. 只启动本队节点，用 `/clock` 的 sim time 接收新鲜 `/odom`、`/scan`、地面图像/CameraInfo、公开抽签。创建官方/候选公开文档规定类型的 `/cmd_vel` publisher，先连续发送全0；可创建两路String上报publisher来核对匹配，但在未实际识别/到点前不发送内容。不得创建用来伪造传感器或裁判完成信号的publisher。
2. 记录创建前后每通道的用户域 subscriber endpoint/type/QoS及本队publisher匹配数量。RELIABLE/VOLATILE可作为**待测的本队发送配置**，不是声称已发现官方QoS。限定等待窗口，例如5秒；建链失败时停止，不改域/名字绕过隔离。
3. 若 `/cmd_vel` 有匹配且本局连续里程计、水平雷达及已确认包络允许，则以 `linear.x≤0.04 m/s`、其他分量0做至多0.5秒直行；位移到0.02m立即停，低速只是本队实验限制，不是赛事限速。运动前/中持续检查本局新鲜雷达的实际扫掠包络、里程计年龄与时钟；失联、障碍、异常漂移或超过时间立即全0。不能用v5静止首帧代替下一局净空。
4. 停止后继续发0一段有界时间，核对公开odom前后位移与速度回零；同时保存运动前后真实地面图像、时间/frame、CameraInfo。若无位移，结束为“命令无可验证响应”；不得以“publish调用未报错”当执行成功。即使短直行成功，也尚未证明非零yaw下的body/world变换或完整地面导航。
5. 本局若仍缺点位ID映射或无目标可见图像，**止于已验证的这次地面动作**。生成控制响应/相机可见性记录供下一步绑定，不发猜测识别或到点声明。失败之后的问题应转成“输出桥/相机/地图哪个合同缺失”，不再重复同一只读探针。

该练习的最低成功证据是：允许命令通道实际匹配，非零地面命令与有界位移在同局关联，停止后实测回零，以及两帧不同位置的真实相机证据。这将把“真实传感器可收”推进到“真实地面控制可用”。

## 地面单点练习的启用条件与验收

在上面的动作响应、**本场首ID到区域映射**和真实识别观测满足后，下一层才启用单点：保留每局公开抽签第一个ID，沿已核对的地面路径到外侧观察位，稳定识别实际类别，发布官方对应地面话术；满足已核对的接受合同后地面进入该区域，停止并发送该ID到点声明。全程不用非零飞行指令。

局内保留观测图、分类结果及置信度、正确话术、原始抽签、到点声明、公开odom/scan、代码哈希和时间。局终读取平台结构化诊断，只有**对应地面任务项识别/到位及实际分数**才记为首点计分成功。即使只得一个点，也比本队日志“任务完成”更能验证规则闭环；若终局仍无计分项，应保留原始结果并定位接受/终局合同，不伪造结束标志。
