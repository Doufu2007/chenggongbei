# v38 连续地面恢复资源实现计划

目标：在冻结v36相机恢复机制上，用独立子类处理已实测的短时clock采样差停车。每次运动的新鲜度、净空、实测停稳与发布前复核不变。32次恢复、单次5秒、累计60秒及全局1200秒均在上传前固定；预算耗尽停止，跨点不清零。

依据：v35三次短暂停车均因clock相对odom落后0.14–0.16秒，三次恢复合计3.291354秒；原全局三次额度不足以支持连续任务。细节见 `docs/ground_three_point_recovery_resource_proposal_v38_20261112.md`。这些样本不支持任何完成率统计。

1. 先用冻结真实guard复现第4次合格恢复被拒绝；补单次/累计/次数耗尽、camera旧epoch与发布门的反例。
2. 新增 `ground_three_point_recovery_budget.py`。仅在最外层接管PAUSE恢复，不虚拟化或重置真实resume_count。恢复当tick仍返回零；下一tick由原运动门重新决定。
3. 相机仍每点最多重采一次，失效worker context不得复用。REPORT_WAIT和已尝试识别后的相机故障、非法数据仍按v36停止。
4. 在 `_budget_fault` 接入单次及累计PAUSE墙钟上限，覆盖watchdog和发布边界。记录每次起止与恢复状态，最多40条，证据覆盖父层的旧max_resumes=3文案。
5. 节点从构造时通过v36内部guard_factory创建新子类；禁止初始化后换guard和全局monkeypatch。新增独立启动器，原文件保持字节一致。
6. 只运行有判别力的专项及必要接线回归，交非作者审查。通过后以v35源码包为冻结基底加入v36/v38模块和新脚本，在官方练习平台验证。

验收：第4次合格恢复可继续；任何不新鲜时只零；单次5秒、累计60秒、32次及原总预算边界均锁停；真实累计路径/角度/时钟不清零。软件通过不等于平台计分。
