# 测评 runner 阻塞核查报告（2026-11-06）

## 结论

当前无法从平台已返回的运行记录定位到源码或启动脚本中的具体错误。最近一次巡检探针测评只返回“裁判”终端的三行启动日志，`terminalLogs=[]`，没有用户脚本首行、编译日志、用户节点日志或退出码。失败原因为“流程未检测到完整结束标志（未提取到成绩）”，只能说明没有提取到有效成绩，不能证明用户脚本没有执行，也不能证明脚本已执行但 ROS 节点没有回调。

## 已核对的证据

- 官方示例脚本使用 `BASH_SOURCE[0]` 定位脚本目录，再由父目录定位工作区；显式 `cd` 工作区后 source ROS Humble 与工作区 `install/setup.bash`。示例中的 `gnome-terminal` 只是启动多个本地终端的写法，不能据此认定平台 runner 必须使用 GUI 或 tab 名。
- 官方指南要求上传 `src` 源码压缩包和只启动本队节点的 `.sh` 脚本；脚本不得启动仿真或裁判。
- 当前源码包满足前端可见的目录预检：存在 `src/inspection_mission/package.xml`，包声明为 `ament_python`，并注册 `interface_probe` 入口。Shell 文件为 LF、无 BOM，`bash -n` 通过。
- 当前探针脚本在 source ROS 前输出唯一启动标记，并在 EXIT trap 输出真实退出码；它按脚本目录、脚本父目录、当前目录和显式工作区定位本队源码，找到后以前台 Python 模块运行。
- 已尝试普通前台 shell、最小 `echo/pwd/sleep`、官方示例风格 `gnome-terminal --window` 和 `--tab` 探针；所有可见结果仍只有裁判日志。更换 tab 标题、增加普通 stdout 或改变终端包装没有产生新证据。
- 前端详情页的日志选择函数明确是：非空 `tabLogs` 优先，否则使用非空 `terminalLogs`，否则无日志；“下载当前终端日志”只是对已返回内容创建本地 Blob，不会请求隐藏的用户日志接口。上传请求只有 `scenarioKey`、源码文件、脚本文件和备注等字段，公开前端没有编译命令、工作目录或日志通道参数。

## 尚未被证实的三种情况

1. runner 没有启动用户脚本；
2. runner 已启动脚本，但 source、编译或加载失败；
3. 用户脚本已运行，但 stdout/stderr 没有进入当前详情接口。

这三种情况在当前平台响应中完全不可区分。由于探针是只读程序且不会发布比赛控制、识别确认或结束消息，即使它成功启动，也不会产生有效裁判成绩。

## 最小阻塞解除请求

应针对同一个 `runId` 请平台方提供以下四项原始信息：

1. 解压后的工作目录和实际执行的启动脚本路径；
2. 编译命令及完整编译返回码/日志；
3. 用户脚本 stdout、stderr 和最终退出码；
4. 评测容器采用的 ROS workspace source 顺序及是否自动 source `install/setup.bash`。

若平台不能提供这些信息，应请其提供一个已知能产生合法结束标志的官方 `demo_inspection_ws.zip` 与配套启动脚本作为同环境对照。继续上传只读探针、重复改用 `gnome-terminal` 或猜测隐藏话题，无法解决当前信息缺口，也会消耗测评次数。
