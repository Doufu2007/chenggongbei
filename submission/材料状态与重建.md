## 重建顺序

在工作区根目录执行。先完成业务变更，再生成当前测试记录及构建记录；重建期间如源码变化，应重新验证相应检查。不要手工把旧 XML 的通过数改成期望值。

```powershell
python -m pytest -q --junitxml=dist/current_tests.xml
python tools/build_submission.py
python tools/create_submission_media.py --junit dist/current_tests.xml --probe-evidence runs/evidence/20261111/callback.jsonl --run-local-scenario
pdftoppm -png -r 100 "submission/城市应急全域巡检技术方案-草稿.pdf" "submission/草稿渲染/page"
```

`build_submission.py` 生成源码包、启动脚本、SHA256SUMS 与 readiness；它不执行正式测评。开发配置未绑定当前官方接口时，即使源码包生成成功，也不等于可以正式提交或已在官方环境运行成功。

`--probe-evidence` 接受接收器原始JSONL，将分析摘要、真实图片（如有）及输入哈希写入PDF旁的 `.probe/` 目录。PDF仅报告实际启动、退出码和收到样本的话题，不把诊断的collected/partial状态解释为裁判得分。更新回调证据时使用新文件，保留旧局原始数据。

逐页查看新生成的 `page-*.png`；若页数减少，旧页图不得混入本次渲染。核对 PDF 中测试表与 manifest 的 JUnit 计数一致，保留失败、错误和跳过的原值。manifest 保存 PDF、流程图、JUnit 和输入证据哈希，变更文件后应重建；它不是整个工作区冻结快照。

## 正式平台材料的入口

以下文件名为用法示例，不表示文件已经存在。仅在取得真实记录后执行：

```powershell
python tools/run_records.py validate runs/records --verify-files --base-dir .
python tools/run_records.py summary runs/records
python tools/create_submission_media.py --mode official --junit dist/current_tests.xml --run-record runs/records/真实完整任务记录.json --video-input runs/evidence/真实完整任务.mp4
```

同一条 `official_task` 台账必须同时有有效裁判结算、明确的完整任务完成、存在且哈希一致的源码包和脚本，并在 `evidence_paths` 中关联该真实 MP4。不能用另一条成功记录给失败记录的录像背书；生成器只校验录像容器/首帧及证据关联，内容仍须人工观看核查。

官方于 2026-11-10 回复：工作空间等文件在官方百度网盘链接中，测评侧构建及运行日志不展示。不可因日志不可见推断脚本未执行或平台故障，验收应依靠有效逐项计分及允许的可见运行观察。

- 当前官方版本的资源与接口核验；第三方公开候选、浏览器演示和本地人工场景均不替代它。
